# Прайсы поставщиков и каталог — решение тестового задания

Я разобрал приложенные данные целиком: прайс Металлсервиса (34 813 строк, 24 склада, две даты вперемешку — свежая августовская и почему-то мартовская 2022 года) и текущий каталог (11 289 карточек, из которых 97,6% висят без привязанного предложения). По итогам спроектировал схему PostgreSQL, поднял её на живой базе и проверил тестами, что запреты, о которых написано в документации, реально срабатывают. Не только на бумаге.

## Что где лежит

- `db/001_schema.sql` — вся схема: 31 таблица в шести слоях, 23 триггера, частичные уникальные индексы. Главный файл.
- `db/002_seed.sql` — справочники. Одна деталь, которой я дорожу: причины исходов взяты не из головы, а из реальной колонки «Почему не привязано» в прайсе — отчёты старой и новой системы будут говорить на одном языке.
- `db/003_views.sql` — витрина `v_site_price` (ровно одна цена на карточку-склад-поставщика) и метрики покрытия.
- `db/tests/001_invariants.sql` — 10 проверок. Каждый раз, когда в документации написано «невозможно», здесь есть тест, который это «невозможно» ловит.
- `docs/` — диагноз, схема с объяснением каждой таблицы, конвейер привязки от файла до сайта, разбор всех 14 контрольных случаев из задания.

Читать советую по порядку: `docs/01-диагноз.md` (почему сейчас привязывается 21,7%), потом `docs/02-схема-бд.md` (что я построил и почему так), потом `docs/03-маппинг.md` (как это работает в динамике).

## Запуск

```bash
docker run -d --name onmi-pg -e POSTGRES_PASSWORD=dev -p 5432:5432 postgres:16-alpine
for f in db/001_schema.sql db/002_seed.sql db/003_views.sql; do
  psql -v ON_ERROR_STOP=1 -h localhost -U postgres -f "$f"
done
psql -h localhost -U postgres < db/tests/001_invariants.sql   # печатает TEST 1..10 OK
```

## Суть решения, если читать только этот файл

Привязка по названию не может работать в принципе: название — это сериализация атрибутов в свободный текст. «Труба ВГП 20х2,8 оцинк. 6 м» и «Труба в/г оц. Ду20 ст. 2,8 L=6м» — один товар, записанный по-разному; «Болт М8х20 5.8» и «Болт М8х20 8.8» — разные товары с почти одинаковым текстом. Сравнивая строки, система принципиально не может разделить эти два случая — она сравнивает следствие, а не причину.

Поэтому у меня товар — это не строка, а **категория + обязательные атрибуты + единица + состояние**. У карточки и у позиции прайса предвычисляется хэш этого набора, и на хэшах стоят уникальные индексы: одинаковые карточки не создаются (товар не дробится), разные не склеиваются (оцинкованная и чёрная труба различаются обязательным атрибутом покрытия — это не «похоже на», это разные хэши).

Второе наблюдение из данных: каталог сам грязный — Ду 80 в названии против Ду 15 в характеристиках, масса швеллера 30П в 4,5 раза меньше табличной, фланцы в тоннах. Матчинг в грязный эталон надёжно привязывает к неправильным карточкам. Поэтому у карточек своя валидация с block-правилами, и привязка к карточке с открытой block-проблемой запрещена на уровне триггера: сначала чиним эталон, потом привязываем.

Третье: все критичные запреты держит база, а не дисциплина кода. Активная привязка на позицию — ровно одна (частичный уникальный индекс), активная цена на позицию и склад — ровно одна, атрибут вне списка категории физически не вставляется (составной FK-замок), а триггер-страж перед активацией привязки сверяет хэши, единицы, политику состояния («НН» по умолчанию скрыт) и block-проблемы. «Срочный фикс-скрипт в обход правил» просто не пройдёт.

Четвёртое: ничего не теряется молча. Каждая строка прайса заканчивается одним из четырёх исходов — привязка, задача человеку с кодом причины, осознанное «вид не возим» или технический отказ загрузки. Счётчики сходятся в отчёте прогона.

Пятое: новая ниша — это данные, а не проект. Электроника из задания подключается INSERT'ами: категории, атрибуты (бренд, модель, память), алиасы («Самсунг» → Samsung). Схема не меняется ни на одну таблицу — в сиде это уже показано на примере смартфонов.

## Спорные места — честно

- EAV для атрибутов вместо колонок. Атрибутов на сущность немного (5–8), а ниши будут меняться — колонки означали бы ALTER TABLE и релиз на каждую нишу. Матчинг при этом идёт по предвычисленным хэшам, так что цена EAV не платится там, где важна скорость.
- Хэш идентичности зависит от состава обязательных атрибутов категории. Поменяли состав — хэши пересчитываются, это фоновая задача, а привязки, подтверждённые человеком, не трогаются. Но об этом надо помнить.
- LLM в каскаде привязки я не закладывал: каскад детерминированный, правила версионируются и прогоняются по эталону (`golden_set`). Поле `method='llm_suggest'` в схеме оставлено — добавить можно без миграций, когда появится потребность.
