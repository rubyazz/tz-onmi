# Маппинг: путь прайса от файла до сайта и правила привязки

## 1. Конвейер (что происходит с файлом)

| Этап | Что делает | Пишет в таблицы | Отказоустойчивость |
|---|---|---|---|
| 1. Приём | Файл складывается в объектное хранилище, считается SHA-256. Повтор файла → `duplicate`, конец | `price_list` | битый файл → статус `failed`, задача админу, ничего не попало в данные |
| 2. Разбор (raw) | Строки кладутся «как есть», без чистки и интерпретации | `price_list_row` (append-only) | строка с мусором остаётся строкой raw; счётчик `rows_total` фиксируется |
| 3. Нормализация | Типизация: категория поставщика, атрибуты через словарь алиасов, числа (запятая/точка, мм/м), единицы, состояние («НН», «уценка»), natural key позиции | `offer`, `offer_snapshot` (diff), `offer_attribute`, `offer_price` | нераспознанное значение → кандидат-алиас + ревью; позиция не пропадает |
| 4. Матчинг | Каскад привязки (§3) | `card_link`, `review_task` | неуверенность → ревью с причиной, никогда «наугад» |
| 5. Валидация | Правила качества по карточкам, ценам, привязкам | `validation_rule`, `validation_result` | `block`-проблема останавливает публикацию затронутых сущностей |
| 6. Публикация | Витрина собирается представлением: активные привязки × активные цены × свежесть × политика состояний | `v_site_price` | идемпотентно: пересбор ничего не дублирует |

Каждый этап — прогон `pipeline_run` со счётчиками исходов: `привязано / в ревью / отказано (код причины) / игнор`. Баланс «строк в файле = сумма исходов» проверяется в конце прогона — это формальный запрет на молчаливую потерю.

## 2. Что такое «один и тот же товар»

```
товар = ( категория
        , канонические значения обязательных атрибутов категории
        , единица продажи
        , состояние )          -- «НН»/«уценка» — другой товар с точки зрения витрины
```

Канонизация значений (до сравнения и до хэша):
- **числа**: к десятичной точке, без ведущих/хвостовых нулей; длины — к мм; «н/д» не число — это значение enum `length_class=nd`;
- **enum**: написание поставщика → `attribute_alias` → `attribute_value.code`; нет алиаса → кандидат-алиас + ревью (не «похоже значит равно»);
- **марки**: словарь марок с нормализацией кириллица↔латиница; «40Х13» = «40X13»; AISI 304 и 08Х18Н10Т — **разные** значения словаря (связь «аналог» заводится отдельно и в идентичность не входит);
- **размеры**: разделители «х»/«x»/«*»/«×» эквивалентны; порядок «толщина×ширина×длина» нормируется правилом категории (для листа — порядок фиксирован, иначе — ревью).

## 3. Каскад привязки позиции

```
1. Категория: supplier_category_map → категория каталога.
   Нет маппинга            → ревью category_unmapped (один раз на категорию, не на строку!)
   Статус ignored          → исход «вид не возим», осознанный, с автором
2. Обязательные атрибуты категории извлечены из позиции?
   Нет                     → ревью missing_required_attribute (в задаче перечислено, чего не хватает)
3. Кандидаты = карточки категории, у которых identity_hash = identity позиции.
   Ровно одна              → card_link active, method=rules_exact, confidence≈1
   Несколько               → дискриминация необязательными атрибутами (ГОСТ, производитель…):
                              осталось одна → rules_disambiguated
                              осталось >1   → ревью multiple_cards_match (кандидаты в payload)
   Ноль                    → а) есть карточка с неполной идентичностью (todo-карточка старого каталога,
                              у которой не хватает тех же атрибутов) → ревью upgrade_card (дозаполнить
                              карточку атрибутами позиции и до-привязать);
                              б) товара в каталоге нет → ревью create_card_from_offer
                              (черновик карточки уже сгенерирован из позиции; мапперы подтверждают)
4. Единицы и состояния: единица позиции ≠ канонической единице категории и конверсия
   не разрешена → ревью unit_mismatch; состояние «НН/уценка» → политика condition_policy
   (hide по умолчанию — безопасный дефолт, отдельная карточка — решением бизнеса).
```

Автопривязка без человека — только на шаге 3 при полном совпадении обязательных атрибутов. Всё остальное — ревью с кодом причины. Это и есть баланс: **не склеить разные товары важнее, чем привязать больше** — неверная привязка стоит дороже (возвраты, споры, доверие), а непривязанная позиция видна в очереди и доходна после разбора.

## 4. Повторные загрузки, изменения правил, ошибки в файле

- **Тот же файл** — `price_list` по SHA-256 → no-op, фиксируется в `pipeline_run`. Случай 12.
- **Новый файл, позиции без изменений** — natural key находит существующие `offer`; `offer_snapshot` не создаётся (пары offer×price_list уже есть), обновляются `last_seen_at` и цены: старой цене ставится `valid_to`, новая вставляется. Дублей нет.
- **Позиция изменилась** (дописали «оцинк.») — изменился natural key → новый `offer`, старый `retired`, его привязка `auto_expired`; diff виден в `offer_snapshot.changed_fields`. Случай 11.
- **Позиция исчезла из прайса** — её активные цены закрываются `valid_to` (нет в витрине), оффер уходит в `retired` после N прайсов подряд (чтобы не мигать). Карточка остаётся, если есть другие поставщики.
- **Изменились правила обработки** — правила версионируются в репозитории (git), прогон пишет `ruleset_version`. Выкат правил = прогон по `golden_set` (эталонная разметка, пополняется из подтверждённых ручных решений): точность/полнота не хуже порогов → выкат; иначе правила не едут. После выката матчинг можно перепрогнать по истории raw — старые привязки, подтверждённые человеком (`method=manual, verified`), не трогаются.
- **Ошибка в файле** (нет цены, кривая кодировка, чужие колонки) — этап приёма/разбора фиксирует отказ по файлу или строке с причиной; частичная загрузка допустима только с явным счётчиком отказов в `pipeline_run`.

## 5. Ручная работа = обучение системы

В очередь попадают не «строки прайса», а **типизированные задачи** с контекстом и ожидаемым действием:

| Тип задачи | Что видит человек | Что происходит после решения |
|---|---|---|
| `new_alias_value` | значение-кандидат, ближайшие канонические значения | approve → алиас в словаре, все такие позиции до-привязываются автматически |
| `multiple_cards_match` | позиция + 2–3 карточки-кандидата с различающимися атрибутами | выбор карточки → привязка; различающий атрибут — кандидат в `required` для категории |
| `missing_required_attribute` | каких атрибутов не хватает, где их взять (спецификация, сайт поставщика) | дозаполнение оффера → автопривязка |
| `create_card_from_offer` | черновик карточки, сгенерированный из позиции | подтверждение → карточка `ready`, привязка автоматически |
| `upgrade_card` | старая карточка с пробелами + позиция с полными данными | дозаполнение карточки → identity пересчитан → привязка |
| `category_unmapped` | категория поставщика + наше дерево | маппинг один раз — дальше вся категория идёт автоматически |

Каждое решение пишется в `card_link` (метод, автор, время) и `audit_log`. Точность каскада растёт от прайса к прайсу: словарь алиасов и обязательные атрибуты категорий пополняются, доля автопривязок растёт, доля ревью падает — это измеримо (метрики ниже).

## 6. Как докажем цифрами (метрики)

- **Покрытие**: % позиций с активной привязкой (сейчас 20,4% строк / 21,7% позиций — точка отсчёта из ТЗ), в разрезе категорий и причин.
- **Точность**: выборочная слепая сверка + `golden_set` как регресс; цель — согласованность правил > 99% (сейчас у двух аналитиков 78%).
- **Скорость ручного разбора**: медиана времени жизни `review_task`, штук в день, доля автопривязок в новом прайсе.
- **Свежесть витрины**: доля цен старше `freshness_days` (сейчас 2 536 строк с датой 2022-03-03 — таких на сайте быть не должно), число карточек с >1 ценой на склад от одного поставщика (сейчас 473 → должно стать 0 структурно).
- **Целостность**: баланс исходов каждого прогона; число открытых `block`-проблем валидации; дублей identity в категории — 0 by design.
- **Деградация замечаем**: контрольные метрики считаются на каждом `pipeline_run`; алерт при падении автопривязки на N п.п. к прошлому прайсу того же поставщика (сменился формат файла — самая частая причина) и при росте доли нераспознанных алиасов.

## 7. Перенос текущего каталога (11 289 карточек, 2 269 привязок)

1. `product` создаётся с сохранением `product_id`, `slug`, `legacy_code`, `work_status`, `problems` — адреса страниц и идентификаторы не меняются, сайт не останавливается.
2. Атрибуты из трёх pivot-колонок + `extra_attributes_json` переносятся в `product_attribute` через словарь (русские имена → коды) с пометкой `source=migration`.
3. Для каждой карточки пересчитывается `identity_hash`; карточки с неполным набором обязательных атрибутов остаются `todo` и попадают в очередь `upgrade_card` — но уже с известным списком пробелов, а не «карточка плохая».
4. Существующие 2 269 привязок переносятся как `card_link(method=legacy_import, status=candidate)`; в пилотных категориях они перепроверяются каскадом: подтвердившиеся → `active` (метод сохраняется в истории), противоречивые (994 конфликта `mapped_exact_offer_conflict` уже известны) → ревью. Внепилотные категории продолжают работать как есть — переключение по категориям, не биг-бэнгом.
